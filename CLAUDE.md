## Что это

Telegram Mini App для студентов ABC Universe (программа Work & Travel /
au pair и т.п.): показывает участнику его текущий этап оформления
(roadmap), документы, платежи, брифинги, мероприятия. Данные приходят из
amoCRM (сделка участника = его карточка), синхронизируются в Google Sheets
через Google Apps Script, который выполняет роль backend — отдельного
сервера (Node/Python) нет и сознательно не нужно, см. раздел
«Ограничения» в конце `SETUP.md`.

Плюс несколько служебных HTML-страниц для координаторов (не для студентов):
`admin.html`, `admin-events.html`, `admin-users.html` — они открываются
координатором в браузере отдельно от Mini App, но используют тот же
backend и тот же `ADMIN_SECRET`.

## Архитектура одним взглядом

```
Telegram (Mini App)  ──┐
admin*.html (браузер) ──┼──►  Google Apps Script (Web App)  ◄──►  Google Sheets (БД)
                        │              │  │
                        │              │  └──►  Wazzup24 API (WhatsApp внутри amoCRM)
                        │              └─────►  amoCRM REST API v4 (сделки участников)
                        │
   фронтенд — статика (index.html + js/ + css/), хостится на GitHub Pages
```

- Фронтенд Mini App: `index.html`, `js/`, `css/` — чистый JS без сборки,
  ES-модули напрямую в браузере. `js/services/config.js` содержит
  `BACKEND_URL` — единственное, что связывает фронтенд с backend. Если
  `BACKEND_URL` пустой — приложение работает на mock-данных
  (`js/services/mockApi.js`), это Phase 1/демо-режим; сейчас он заполнен,
  значит приложение уже «живое» (`js/services/liveApi.js`).
- Backend: папка `backend-apps-script/` — 9 файлов `.gs`, живут **не**
  в этом гите как исполняемый код, а как зеркало того, что вручную
  скопировано в реальный проект Google Apps Script (см. «Живая
  инфраструктура» ниже). Это важно: **правки в `backend-apps-script/*.gs`
  в этом репозитории сами по себе ничего не меняют** — их нужно ещё
  руками (через браузер, script.google.com) перенести в реальный
  Apps Script проект и передеплоить. Как это делать — см. раздел ниже.
- БД: Google Sheets, схема — `SHEET_SCHEMA` в `backend-apps-script/Setup.gs`.
- Координаторские инструменты (`admin.html` и т.п.) — статические файлы,
  хостятся вместе с Mini App на том же GitHub Pages, но открываются
  координатором напрямую по URL, не через Telegram. Вход — по паролю
  `ADMIN_SECRET`, хранится в localStorage браузера координатора.

## Секреты (Script Properties в Apps Script — НЕ в гите)

Все значения живут в Apps Script → Project Settings (шестерёнка) →
Script Properties. В коде — только имена ключей (`CFG("...")` в
`Config.gs`), реальные значения никогда не коммитятся. Полный список с
пояснениями — шапка комментария `Config.gs`. Коротко:

Обязательные: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`,
`AMO_SUBDOMAIN`, `AMO_ACCESS_TOKEN`, `WEBHOOK_SECRET`, `SHEET_ID`,
`ADMIN_SECRET`.

Условно обязательные: `AMO_CLIENT_ID`/`AMO_CLIENT_SECRET`/
`AMO_REDIRECT_URI`/`AMO_REFRESH_TOKEN` — нужны, только если используется
обычный OAuth-обмен токена amoCRM. Если вместо этого выписан
«долгосрочный токен» (Долгосрочный токен, ~1 год жизни) прямо в
Ключи и доступы amoCRM — можно оставить только `AMO_ACCESS_TOKEN`, эти
четыре не нужны (см. комментарий над `getAmoAccessToken_()` в
`AmoCRM.gs`). **Так это сейчас и настроено** — не считай их отсутствие
багом, если увидишь через диагностику.

Опциональные: `WAZZUP_API_KEY`, `WAZZUP_CHANNEL_ID` (WhatsApp через
Wazzup24, см. ниже), `LINK_TOKEN_TTL_HOURS`, `STATUS_ID_MAP_JSON`,
`FIELD_ID_*` (числовые ID кастомных полей amoCRM).

## Повторный самоаудит и найденный пробел с триггером (09.09.2026)

По просьбе владельца («перепроверь сам себя, в тестах, в отправках
сделок, уведомлениях итд») повторно и более скептически проверена вся

- **Цепочка уведомлений о смене этапа сделки** прослежена целиком и
  подтверждена рабочей: вебхук amoCRM → `doPost` → `Webhooks.gs` →

- **Живой бэкенд**: 0 реальных сбоев в трафике `doPost`/`doGet` за

`sendPendingEventInvites()` (`Events.gs`) триггер не требуется —

## Платёж 3: автоматический дедлайн +4 месяца (09.09.2026)

По договору сроки оплаты: платёж 1 — 5 дней, платёж 2 — 30 дней,
платёж 3 — 4 месяца с момента создания сделки. Платежи 1 и 2 уже
считались автоматически (`FIXED_PAYMENTS_` в `Webhooks.gs`, без
изменений). Платёж 3 же был полностью ручным — ни дедлайна, ни суммы
по умолчанию не было, координатор вводил дату дедлайна вручную в поле
FIELD_ID_PAY3_DEADLINE в amoCRM, либо не вводил вообще (0 триггеров /
0 расчёта — реальные дедлайны платежа 3 никогда не выставлялись
автоматически).

Пользователь подтвердил: оставить 5 и 30 дней как есть, добавить
автоматический расчёт дедлайна платежа 3 (+4 месяца от даты создания
сделки) для всех студентов по умолчанию. Индивидуальная договорённость
— исключение: если координатор вручную указал дату в
FIELD_ID_PAY3_DEADLINE на карточке сделки, она перекрывает
автоматический расчёт (`manualDeadline || autoDeadline` в
`syncVariablePayment3_`).

Изменение внесено в `backend-apps-script/Webhooks.gs`, синхронизировано
во все три копии (диск / живой Apps Script / GitHub-зеркало,
коммит `34a7ad3`). Сумма платежа 3 (`FIELD_ID_PAY3_AMOUNT`) по-прежнему
вводится координатором вручную — только дедлайн стал автоматическим.

   другие раньше и только в live-редакторе/через отдельный upload) —
   и это нормально для воркфлоу с ручным зеркалированием, не считать
   «всё с одной стороны новее» само собой разумеющимся.

   бэкенд — `backend-apps-script/*.gs` в гите лишь зеркало для истории,

   вручную (см. «Как редактировать backend» ниже), его я не трогал.

   Telegram» обещала 4 напоминания перед визовым интервью. Такой рассылки
   в `Reminders.gs` нет и не было (там только `sendPaymentReminders_` и
   `sendCieeActivationReminders_`). Удалены обе части — поле в конфиге и
   рендер в `statusDetail.js`. Возвращать только вместе с реальной
   рассылкой и time-driven триггером. Дата интервью и обратный отсчёт на
   этом экране настоящие, они из `VisaInfo`.
3. **`Participants.name` — это название сделки amoCRM**, а не имя
   человека (кладёт `syncParticipantFromDeal_` в `Webhooks.gs`). Имя
   убрано из приветствия на главной: теперь просто «Добрый день 👋».

   вернуть обращение по имени — заводить в amoCRM отдельное поле «имя для

данным, которые выглядят как персональные.** Конфиг этапов — это копия
интерфейса, одинаковая для всех; всё, что должно отличаться у разных
студентов, приходит из Sheets через `Api.gs`.

## Как редактировать backend (важно!)

Файлы в `backend-apps-script/*.gs` в этом гите — это зеркало/источник
правды для истории и ревью, но **сам живой код исполняется в отдельном
Apps Script проекте** (URL см. выше), и правки туда переносятся вручную
через браузер (Claude in Chrome / desktop bridge browser tools), а не
автоматическим деплоем из гита.

**Осторожно с `Config.gs`:** это единственный файл, где живая версия
исторически оказывалась НОВЕЕ репозитория, и на 03.09.2026 копии
совпадают по содержанию (тексты, `STAGE_IDS`), но расходятся в
комментариях — живая версия авторитетна. Не заменяй его целиком из
репозитория, правь точечно. Перед любой заменой файла в живом проекте
полезно построчно сравнить его с репозиторной копией и глазами
посмотреть, какие строки исчезнут: так уже находились комментарии,
которых в гите не было.

Рабочий процесс, который использовался
до сих пор:

1. Написать/поправить код сначала в файле в этом репозитории (проще
   проверить синтаксис — `node --check <файл>.js` после копии с
   расширением `.js`, `.gs`-синтаксис почти полностью совместим с
   обычным JS).
2. Закоммитить в гит.
3. Открыть тот же кусок кода в живом редакторе `script.google.com`
   (через браузерные инструменты) и внести те же изменения руками —
   печатать через `type()`, не копипастой (буфер обмена не всегда
   надёжен в автоматизации браузера).
4. **Обязательно визуально сверить результат** (скриншот/zoom) на
   лишние/пропавшие фигурные скобки перед сохранением — редактор Apps
   Script при автозакрытии скобок (когда печатаешь `{` и Enter) иногда
   дублирует закрывающую `}` в неожиданном месте, а иногда — нет,
   предсказать нельзя. Это происходило несколько раз именно в этом
   проекте и один раз почти привело к потере файла из-за незакрытого
   `if`. Через `Ctrl+A` + `Delete` над стандартным `function myFunction()
   {}` иногда не полностью очищает шаблон — тогда строка `function
   myFunction() {` остаётся первой строкой файла, а твой код
   вставляется ВНУТРЬ неё; тоже нужно визуально проверять первую
   строку файла после вставки, не только последнюю.
5. Сохранить (кнопка «Сохранить проект на Диск» либо `Ctrl+S`) и
   **перепроверить в свежей вкладке** того же URL проекта, что
   изменения реально сохранились на сервере — индикатор «Сохранено»/
   «Несохранённые изменения» в самой вкладке иногда не отражает
   реальность, если файл был структурно сломан в процессе редактирования.
6. Создать новый деплой версии (Начать развёртывание → Управление
   развёртываниями → редактировать активный деплой → Версия: «Новая
   версия» → Начать развёртывание) — без этого шага правки в редакторе
   не попадут в реальный `BACKEND_URL`, который обслуживает
   Telegram/amoCRM/фронтенд (Web App деплой — это застывший снимок кода,
   а не «живой HEAD»).
7. Имена функций, заканчивающиеся на `_` (например
   `adminListAllParticipants_`), Apps Script по конвенции прячет из
   выпадающего списка «Выполнить» — это нормально, они вызываются только
   из другого кода, не напрямую руками. Для ручного тестового запуска
   через UI нужна функция без `_` в конце.

## Тестирование / диагностика без пароля ADMIN_SECRET

Есть безопасный способ проверить, что роуты подключены, не зная секрет:
запрос с заведомо неверным `secret` должен вернуть чистый JSON
`{"error":"bad secret"}`, а не HTML-страницу с ошибкой сервера — если так,
значит код на сервере синтаксически цел и роут существует. Для более
глубокой проверки (Script Properties, чтение Sheets, вызов внутренних
`_`-функций) — удобно временно создать новый `.gs`-файл в живом
редакторе с диагностической функцией (имя без `_`, чтобы попало в
список «Выполнить»), прогнать её, посмотреть Журнал выполнения, потом
файл удалить (Меню файла → Удалить) — это не требует пересоздания
деплоя, если сам временный файл никогда не деплоился отдельно.
